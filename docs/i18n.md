# i18n Developer Guide

## Overview

WhyNot uses **react-i18next** in both frontends and **i18next** with filesystem backend in the gateway. Five languages are supported: English (en), Arabic (ar), French (fr), German (de), and Spanish (es). Arabic triggers RTL layout via `<html dir="rtl">`.

## Adding a New Translation String

### Frontend (frontend/ or admin-frontend/)

1. Pick the namespace that fits your string (e.g. `dashboard`, `settings`, `billing`).
2. Add the key to `public/locales/en/<namespace>.json`:

```json
{
  "dashboard.newWidget.title": "My Widget"
}
```

3. Add the same key to all other locale files (`ar`, `fr`, `de`, `es`) — use English as placeholder until translated.

4. Use in a component:

```tsx
import { useTranslation } from 'react-i18next';

function MyWidget() {
  const { t } = useTranslation('dashboard');
  return <h2>{t('dashboard.newWidget.title')}</h2>;
}
```

### Gateway

1. Pick the namespace (`errors`, `success`, `emails`, `validation`, `billing`).
2. Add the key to `gateway/src/i18n/translations/en/<namespace>.json`.
3. Add the same key to ar/fr/de/es files.
4. Use via `req.t()`:

```ts
res.status(404).json({
  error: { code: 'NOT_FOUND', message: req.t('errors:resource.notFound', { resource: 'Widget' }) }
});
```

## Completeness Tests

Each project has an `i18n-completeness.test.ts` that asserts:
- All 5 languages have the same set of namespace files.
- Every namespace has the same key tree across all languages (recursive comparison against `en`).

Run tests:
```bash
docker compose exec frontend npx vitest run src/__tests__/i18n-completeness.test.ts
docker compose exec admin-frontend npx vitest run src/__tests__/i18n-completeness.test.ts
docker compose exec gateway npx vitest run src/__tests__/i18n-completeness.test.ts
```

## RTL Support

Arabic is the only RTL language. When the user switches to Arabic:
1. `i18n.changeLanguage('ar')` fires.
2. `useDirection()` hook reads `i18n.resolvedLanguage` and sets `document.documentElement.dir = "rtl"`.
3. All CSS logical properties (`ms-`, `me-`, `ps-`, `pe-`, `text-start`, `text-end`) flip automatically.
4. Directional icons use `rtl:scale-x-[-1]` for mirroring.

**Never use `rtl:flex-row-reverse`** — native `dir="rtl"` handles flex reversal.

## Accept-Language Flow (Gateway)

1. Client sends `Accept-Language: fr,en;q=0.9` header.
2. `i18nMiddleware` parses the header with `accept-language-parser`.
3. Best match from supported languages is selected (falls back to `en`).
4. `req.lang` is set to the matched language code.
5. `req.t(key, vars)` translates using the matched language.
6. Error responses use `req.t()` for localized messages.

## Language Switcher

Both frontends include a `<LanguageSwitcher />` component in the header. It:
- Shows a globe icon dropdown with all 5 languages (native names + flag emoji).
- Calls `i18n.changeLanguage(lang)` on selection.
- Updates `<html lang>` and `<html dir>` attributes.
- Persists choice in `localStorage` under `i18nextLng`.

## Translation Update Process

WhyNot supports 5 languages: **English (en)**, **Arabic (ar)**, **French (fr)**, **German (de)**, **Spanish (es)**.

### Adding or Updating Translations

1. **Add the English key first** in the appropriate `en/<namespace>.json` file.
2. **Add the same key** to all 4 non-English locale files (`ar`, `fr`, `de`, `es`) with proper translations.
3. **Consult the glossary** at [`docs/i18n/glossary.md`](./i18n/glossary.md) for brand terms that must NOT be translated and for consistent term mappings across languages.
4. **Run completeness tests** to verify all keys are present and translated:
   ```bash
   docker compose exec frontend npx vitest run src/__tests__/i18n-completeness.test.ts
   docker compose exec admin-frontend npx vitest run src/__tests__/i18n-completeness.test.ts
   docker compose exec gateway npx vitest run src/__tests__/i18n-completeness.test.ts
   ```

### Translation Quality Standards

- **Arabic**: Modern Standard Arabic, formal register. Full plural set (`_zero`, `_one`, `_two`, `_few`, `_many`, `_other`) for keys with `{{count}}` interpolation.
- **French**: Formal "vous" form. Never use "tu".
- **German**: Formal "Sie" form. Never use "du".
- **Spanish**: Latin American-neutral. Formal "usted" form. Avoid Spain-specific terms.

### Completeness Tests

Tests assert three things:
1. **Key parity** — every language has the same namespace files and key trees as English.
2. **No English leftovers** — non-English values must differ from their English counterpart (brand terms excepted via allow-list).
3. **Interpolation preservation** — keys with `{{variable}}` placeholders must contain those placeholders in all languages.

### Glossary

See [`docs/i18n/glossary.md`](./i18n/glossary.md) for:
- Brand terms that must never be translated (WhyNot QA, QA Loop, MCP, etc.)
- Consistent term mappings across all languages
- UI placeholder values to preserve
- Formality register per language
